# Блокноты: оформление и workflow

Эталон — `notebooks/example_model.ipynb` (17 детекторов). Новые детекторы
повторяют структуру блока ARIMA, меняя только обучение и score.
При расхождениях ориентир один — `example_model.ipynb` и `report/Отчёт.tex`.

## Структура блокнота

1. Гиперпараметры (общие): `TEST_SPLIT_1/2`, `MCC_BAND`, `PLOT_TAIL`,
   `MAP_FIGSIZE`, `ALLOWED_STATUS`; для оконных torch-моделей — `N_WINDOWS`,
   `N_EPOCHS`, `TORCH_BATCH_SIZE`, `TORCH_INFER_BATCH`, `TORCH_LR`.
2. Импорты: одна code-ячейка сразу после констант; все `import` / `from`
   только там.
3. Предобработка: одна функция = один шаг, цепочка вызовов в конце ячейки.
4. Общая markdown-ячейка «Используемые метрики» (MCC для порога, DL;
   positive class = **anomaly**, `label` 0).
5. Общая code-ячейка хелперов: метрики, порог, operational DL,
   `fmt_num` / `nfmt`, окна и кинематика — всё, что используется двумя
   и более моделями.
6. На модель: markdown (теория) + code (константы модели, её функции
   и классы, эксперимент на df1 и df2).

Логику эксперимента держать в блокноте, не выносить в `app/` без явной
просьбы. Google docstrings, около 120 символов в строке.

## Константы и код модели

- Константа одной модели (`MPCT_*`, `LSTM_*`, …) объявляется в начале
  code-ячейки этой модели, не в общей ячейке гиперпараметров.
- Функция или класс, вызываемые только из одной модели, объявляются в той же
  ячейке перед циклом сценариев. Общие хелперы (`evaluate_test`,
  `window_starts`, `track_shape_index`, …) остаются в общей ячейке.
- Не дублировать объявления: если константа уже задана в ячейке модели,
  второе присваивание — ошибка.

## Markdown моделей

- Без цветового оформления (в том числе без inline-кода в тексте ячейки —
  в Jupyter он подсвечивается) и без лишнего полужирного текста.
- Полужирным допускаются ключевые определения классов (**move**, **anomaly**)
  и при необходимости одно имя метода в заголовке; формулы — в `$…$`
  и `$$…$$`.
- В общих ячейках («предобработка», «Используемые метрики») — без
  декоративного полужирного; классы в тексте — `$\mathrm{move}$`,
  `$\mathrm{anomaly}$` или **anomaly** там, где явно задан положительный
  класс.

## Метрики test (только «Список метрик» в Отчёте)

`TEST_REPORT_METRICS` — фиксированный порядок:

- Гео: `rmse_m`, `max_deviation_m`, `distance_loss_m`
- Время: `delay_median`, `delay_mean`, `delay_p95`, `delay_max`,
  `delay_n_on_time`, `delay_n_late_or_missed`
- Классификация: `precision`, `recall`, `f1`

Счёт: `evaluate_test` → `TrajectoryMetrics.compute_all`. В итоговых таблицах
test не показывать: MCC, DLR, train-метрики, порог, время, heatmap метрик.
MCC, operational DL и подобранный порог выводятся в `print` при подборе
порога на train.

## Таблицы

- `test_report_row` + `display_test_report_table`.
- Формат чисел: `fmt_num` (при |x| ≥ 1000 — `_`), `nfmt` для целых
  с пробелом.
- Перед `display` столбцы метрик прогонять через
  `.map(lambda v, k=key: _format_metric_value(k, v))`, не полагаться
  на `Styler.format` с lambda на два аргумента.

## Порог (train)

Сетка по score → максимум MCC; в полосе `MCC_BAND` от лучшего MCC → минимум
operational distance loss (move-цепочка ENU). На test тот же порог
без подгонки.

## Вывод code-ячейки модели (4 шага, без дублирования карт)

1. Сводная таблица df1 + df2.
2. Одна карта эталона: `plot_track_maps(..., map_panel="ground_truth")`
   на хвосте test df1 (`PLOT_TAIL`).
3. Для каждого сценария: таблица одной строки + карта модели
   `map_panel="model"`.
4. Не дублировать карту эталона в блоках по сценариям.

Карты: `app/viz/track_osm.plot_track_maps`, `annotate=False`,
`figsize=MAP_FIGSIZE`, `slice_trajectory_series`.

BBox: по истинным **move** (`label == 1`) на отображаемом участке плюс 5 %
размаха с каждой стороны; обрезка линий по окну — ожидаемо. `bbox=None` →
авто через `bbox_from_move_points`.

## Разметка

`y == "anomaly"` → `label 0`; предсказание anomaly → `0.0`, move → `1.0`
в `TrajectorySeries`.

## Гигиена ячеек

- Докстринги без пустых `Args` / `Returns`: либо описать параметры, либо
  убрать секцию.
- Удалять неиспользуемые импорты и константы.
- Правки стиля и массовые переносы делать по одной модели за раз, чтобы
  при сбое пострадал один блок.

## Завершение работы над моделью (только после подтверждения)

Когда модель в блокноте готова и пользователь явно подтвердил завершение
(не раньше):

1. Актуализировать `report/Отчёт.tex`: описание метода, параметры, порядок
   эксперимента, согласованность со списком метрик.
2. Актуализировать `docs/notes/methods.md`: формулы, score, обучение, порог,
   отличия от других методов, ссылка на блокнот.

Без явного подтверждения правки в Отчёт и `methods.md` не делать проактивно
по ходу черновой работы в блокноте.
